## Part A: the spike (Task 1)

- **What it shows:** the install-moment decision of spec §6.2 (U1–U7 in the plan's table) with a build of this branch's own code, signed with an ephemeral key, against a `latest.json` served inside the guest.
- **When:** after Task 5 is committed (U2 needs Task 4's notify card, U4 needs Task 5's re-apply to be absent for a reason); run earlier, U4's "no `update reapply=` line" is recorded as not proving the re-apply.
- **The build:** CI's artifact `cmdstudio-updater-spike` of a `workflow_dispatch` run of `ci.yml` on this branch with `updater_spike` on (`gh workflow run ci.yml --ref phase4b -f updater_spike=true`, after the controller's push). **One download, with the founder's explicit yes first:** `gh run download <run id> --name cmdstudio-updater-spike --dir <scratchpad>\p4b-spike`. The folder holds the two installers, their `.sig` files, `latest.json`, `latest.same.json`, `latest.bad.json` and `spike.key.pub`. Record the commit and the run id in `results.md`.
- **Setup (once per host session):** Windows PowerShell 5.1 on the host, from the repo root: `. .\spikes\vm\vm.ps1`, `. .\docs\spikes\phase3-vm-check\helpers.ps1`, `. .\docs\spikes\phase4-install\helpers.ps1`, `. .\docs\spikes\phase4-update\helpers.ps1`; `$spike = '<scratchpad>\p4b-spike'`; `$a5bLines = 'update installing|update installed|recovery_entry|pause |cmd=recovery_status'` (A5b's log filter, set here because a `|` cannot stand in the table). Per VM, and again after every `Start-CleanVm`: `$vm`, `$u` as 4a's protocol sets them; `Start-CleanVm $vm $u`; `Install-Phase4bSetup $vm $u $spike` (prints `same file in the VM: True` twice); `Invoke-GuestDesktop $vm "$($P4B.Guest)\guard.test.ps1" '' $u` must end with the computed total of checks passing (`guest guards: 49/49 checks pass`: 23 guarded scripts, two checks each, and three more); `Start-Phase4bServer $vm $u` (prints `answers: True`, read inside the desktop task); then, the task gone, `Test-Phase4bServer $vm $u`, a separate guestcontrol call, must print `server up: True` and `server pid <n> running: True` (the listener outlived the task that started it; `update-server.ps1 -Start` creates it through WMI, `Win32_Process` `Create`, so it is not the task's child); `Set-Phase4bLatest $vm latest $u`. If `Test-Phase4bServer` prints `server up: False`: record it in `results.md` (the finding is that the WMI-created listener did not outlive the desktop task), do not run A1 (its check would log `offline` and show nothing), and try once to start it outside the desktop: `Stop-Phase4bServer $vm $u` (removes the stale `server.pid`), then `Invoke-GuestPs $vm "& '$($P4B.Guest)\update-server.ps1' -Start -Root '$($P4B.Setup)'" $u 60` and `Test-Phase4bServer $vm $u` again; still `False` stops part A and goes to the controller. A second `Start-Phase4bServer` while one runs is refused (`-Stop first`).
- **The modes:** the app's first start after an install is in automatic mode, and its check would download and its close would install (U3) before the step that tests it: so every set-up run installs silently (no app start), sets **notify** before the first start, and switches to automatic only in the step that tests the close (A3) or the offline case (A7).
- **How results are judged:** by `update-check.ps1`'s printed lines (`installed:`, `log:`, `updateJson:`, `updates:`, `runJson:`, `processes:`), by `Wait-Phase4bVersion`'s seconds, by `Get-Phase4bServerLog`'s request lines, by `Test-Phase4bServer`'s `server up:`, by `Get-Phase4bLogLines`' matching lines (the log lines that are not the updater's), and by screenshots where nothing prints (the cards, no window after a close).
