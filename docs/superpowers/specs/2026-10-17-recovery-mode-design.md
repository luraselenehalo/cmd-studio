# CMD Studio — โหมดกู้คืน (recovery mode)

- **วันที่:** 2026-10-17
- **สถานะ:** founder อนุมัติเมื่อ 2026-10-17 ("โอเค เขียนแผนต่อได้เลย") สิ่งที่ปรับหลังเขียนแผน 3b-1 อยู่ใน §13
- **เป็นงานของ:** phase 3b ซึ่งทำหลัง phase 3 (วิซาร์ด หน้าแรก ช่วยเหลือ) และก่อน phase 4 (ตัวอัปเดตและตัวติดตั้ง)
- **สเปกหลัก:** `docs/superpowers/specs/2026-10-10-cmd-studio-design.md` เอกสารนี้อ้างหัวข้อของสเปกหลักเป็น §x.y ถ้าเอกสารนี้ขัดกับสเปกหลัก ให้ถือเอกสารนี้ในเรื่องของโหมดกู้คืน

## คำตัดสินของ founder (2026-10-17)

- ขอให้มีระบบกู้คืน "เอาไว้เป็นระบบกับโปรแกรมค้างหรือเกิดข้อผิดพลาดโดยไม่คาดคิด เราจะทำให้โปรแกรมเราไม่ตายง่ายๆ"
- ครอบทั้ง 4 กรณี:
  1. cmd ค้างหรือแครชเพราะธีม
  2. แอปเปิดไม่ขึ้นหรือแครชซ้ำ
  3. แอปค้างระหว่างใช้
  4. แครชที่ไม่คาดคิด พร้อมการแจ้งปัญหา
- ถ้า cmd พังซ้ำ ให้ CMD Studio หยุดธีมเอง และมีทางลัด "CMD Studio Recovery" ในเมนู Start ด้วย
- ทำเป็น phase ของตัวเองหลัง phase 3 เพราะการอัปเดตอัตโนมัติของ phase 4 ต้องมีทางกู้คืนก่อน
- เลือกทาง ก.: ใส่ตัวนับใน `init.lua`, อ่าน event log ของ Windows และมีทางลัด Recovery โดยไม่แตะรูปแบบ AutoRun

## §0 สิ่งที่ต้องยืนยันก่อนเขียนโค้ด

### ยืนยันในโค้ดที่มีอยู่ (grep และอ่านทั้งตัว ไม่ใช่แค่ดูว่าชื่อมี)

- `cmdstudio_core::cleanup::revert_all(sys, ctx) -> Result<Report, ActionError>` (`crates/core/src/cleanup.rs`) ใช้หยุดธีมระดับเครื่อง ต้องอ่านว่าทำอะไรกับ `state.json`, จุดย้อนกลับ และ `incomplete.json`
- `Paths` (`crates/core/src/plan.rs`): `data`, `generated()`, `logs()`, `webview()` และ `settings_file()` โฟลเดอร์ใหม่ของเอกสารนี้เพิ่มเป็นเมธอดของ `Paths`
- `generate::lua::init_lua` และ `banner_lua` (`crates/core/src/generate/lua.rs`):
  - `init.lua` โหลดผลของ `oh-my-posh init cmd` ผ่าน `io.popen`
  - `banner.lua` พิมพ์กล่องต้อนรับใน `clink.oninject` และกันการพิมพ์ซ้ำด้วยตัวแปร `CMDSTUDIO_BANNER`
  - ข้อเดิม "never raises and never prints" ของ init.lua ต้องคงไว้ ยกเว้นบรรทัดแจ้งหยุดธีมใน §3.3
- `run_gui`, `open_main_window` และ `console::fatal` (`app/src-tauri/src/lib.rs`, `console.rs`) รวมถึง callback ของ `tauri_plugin_single_instance`
- `main.rs`: ไม่มี argument เปิดแอป มี argument เป็น CLI ส่วน `--recovery` ต้องเปิดแอป ไม่ใช่ CLI
- `backend::diagnostics::redact`, `redact_sids` และ `user_name_of` ใช้กับบันทึกแครช
- `ipc::handler()` และ `caught(...)` (panic ในคำสั่งคำนวณกลายเป็น `E_INTERNAL`) ส่วน `Cargo.toml` ห้ามตั้ง `panic = "abort"` (ข้อนี้คงไว้)
- UI:
  - `StartNotices` และ `ErrorBoundary` ที่ใช้ `CrashNotice` ร่วมกัน
  - `start.tsx`
  - `Ipc` interface และ mock
  - หน้า Help แท็บแจ้งปัญหา
- เวลาที่ใช้ธีมครั้งล่าสุด: หาว่า `state.json` หรือ manifest ของจุดย้อนกลับเก็บไว้ที่ไหนและเป็นชนิดอะไร ถ้าไม่มี ให้แผนเพิ่มโดยไม่ทำให้ `state.json` รุ่นเก่าอ่านไม่ได้
- `mlua = { version = "0.10", features = ["lua52", "vendored"] }` เป็น dev-dependency ของ core อยู่แล้ว (`crates/core/tests/banner_lua.rs`)

### ต้องลองบน VM ก่อน (spike ต้นสุดของ phase ห้ามเดาเอง)

- **Clink 1.9.34 ต้องมีสิ่งเหล่านี้:**
  - `os.getpid()`
  - การเขียนและลบไฟล์ด้วย `io.open` และ `os.remove` บน path ที่มีอักษรไทย
  - วิธีอ่านรายชื่อไฟล์ใน `health\`, เช่น `os.globfiles`
- **จุดที่นับว่า "ถึง prompt แรกแล้ว"** ต้องอยู่หลัง prompt filter ของ OMP คืนค่า เพื่อให้นับรวมกรณีที่ OMP ค้างด้วย ให้ลองว่า `clink.onbeginedit` ทำงานก่อนหรือหลัง prompt filter ถ้าก่อน ให้ใช้ prompt filter ของเราเองที่มี priority ต่อจากของ OMP ผลที่ได้ต้องบันทึกใน spike
- **เวลาที่เพิ่ม:** วัดเวลาเปิด cmd ก่อนและหลังมีตัวนับ เป้าคือเพิ่มไม่เกิน 5 ms ต่อหน้าต่าง (G13 เคยวัด 14 ms ของ AutoRun ทั้งหมด)
- **Application event log:** event 1000 ของ provider "Application Error" ที่เกิดจาก cmd.exe แครชใน DLL ของ Clink จริง ต้องดูว่า field ใน EventData ชื่ออะไร และค่าเป็นอะไรบน Windows ภาษาไทยและอังกฤษ ข้อความที่จัดรูปแล้วแปลตามภาษาของเครื่อง จึงห้ามใช้ ให้อ่าน EventData ตรงๆ
- **WebView2 `ProcessFailed`:** Tauri ตามเวอร์ชันที่ pin ไว้ต้องเข้าถึงได้ (ผ่าน `with_webview` กับ controller ของ WebView2) และต้องรู้ว่าถ้า renderer แครชหรือไม่ตอบสนอง จะโหลดหน้าใหม่ได้ไหม ถ้าทำไม่ได้ ให้ตัดข้อ §6.4 ออกจาก phase นี้ แล้วบันทึกเหตุผลไว้ใน ruling
- **รอยต่อกับข้อมูลจริง:** event log, `GetProcessTimes` ของ pid ที่ใช้ซ้ำ และพฤติกรรมของ Clink คือจุดที่ของจริงอาจต่างจาก adapter ปลอม ทุกข้อต้องมีเทสต์บน VM อย่างน้อยหนึ่งครั้ง (§10)

## §1 เกณฑ์สำเร็จ

1. **cmd พังติดกันเพราะธีม:** cmd ค้างหรือแครชหลัง Clink โหลดธีม (เช่น OMP ค้าง, OMP แครช หรือ Lua error ก่อนถึง prompt) ติดกัน 3 ครั้ง หน้าต่างที่ 4 ต้องเปิดได้ด้วย prompt ธรรมดาของ cmd โดยผู้ใช้ไม่ต้องทำอะไร และหน้าต่างนั้นบอกเป็นภาษาอังกฤษบรรทัดเดียวว่าธีมถูกหยุดไว้
2. **cmd แครชใน DLL ของ Clink:** ถ้า cmd แครชก่อน Lua จะได้ทำงาน เปิดแอปหนึ่งครั้ง หรือกด "CMD Studio Recovery" หนึ่งครั้ง แล้ว cmd หน้าต่างใหม่ต้องเปิดได้
3. **แอปเปิดไม่สำเร็จ:** ถ้าแอปเปิดแล้วพังก่อนหน้าแรกขึ้น 2 ครั้งติด ครั้งที่ 3 ต้องเปิดเป็นโหมดกู้คืน ซึ่งกดย้อนทุกอย่างได้
4. **แอปแครชระหว่างใช้:** ครั้งต่อไปที่เปิดต้องบอกว่าปิดไปแบบไม่ปกติเมื่อไหร่ และไปถึงหน้าแจ้งปัญหาที่แนบข้อมูลไว้แล้วได้ใน 2 คลิก
5. **แอปค้างระหว่างใช้:** ทุกคำสั่งที่รอนานต้องบอกว่ายังทำงานอยู่ ไม่มีหน้าจอที่ค้างเงียบ และมีทางเริ่มแอปใหม่ที่ไม่ทำให้เครื่องอยู่ในสถานะครึ่งๆ กลางๆ
6. **ข้อจำกัด:**
   - ไม่ส่งข้อมูลใดออกจากเครื่องเองอัตโนมัติ
   - ไม่มีภาษาไทยในสิ่งที่เขียนลงหน้าต่าง cmd
   - กล่องข้อความของ Windows เป็นภาษาอังกฤษ เพราะ UI ยังไม่ขึ้น
   - ไม่เปลี่ยนรูปแบบส่วนของเราใน AutoRun (§5.4)
   - ไม่ต้องใช้สิทธิ์ admin

## §2 สิ่งที่มีอยู่แล้ว (phase นี้ใช้ต่อ ไม่สร้างใหม่)

- ทรานแซกชันที่มี journal: ถ้าโปรแกรมดับกลางทาง คำสั่งที่เปลี่ยนเครื่องคำสั่งถัดไปจะย้อนให้ (`E_TXN_INTERRUPTED`) ถ้าย้อนไม่ครบจะบอกส่วนที่คืนไม่ได้พร้อมวิธีแก้ด้วยมือ (§5.5)
- ล็อก `cmdstudio.lock` ให้ทำทีละคำสั่ง (`E_BUSY`)
- โปรแกรมย่อยที่แอปเรียกมีเวลาจำกัดแล้วถูกปิดทิ้ง (`WinProcess` ใน `adapters/windows/process.rs`) ส่วนการอ่านไฟล์มีเส้นตาย 10 วินาที
- panic ในคำสั่งคำนวณกลายเป็น `E_INTERNAL` และ panic ใน listener ของความคืบหน้าไม่หยุดการใช้ธีม
- UI มี `ErrorBoundary` และถ้าเลือก IPC ไม่ได้จะแสดงประกาศ `E_INTERNAL` พร้อมปุ่ม Reload (phase 3)
- เปิดหน้าต่างไม่ได้ (เช่นไม่มี WebView2) จะแสดงกล่องข้อความแล้วจบด้วย exit code 1
- guard `if exist` ใน AutoRun ทำให้ cmd ยังเปิดได้เมื่อไฟล์ของเราหายไป
- ย้อนทุกอย่าง, จุดย้อนกลับ, `--cleanup` และข้อมูลวินิจฉัยที่ลบชื่อผู้ใช้และ SID แล้ว

## §3 ฝั่ง cmd: ตัวนับใน `init.lua`

### 3.1 ไฟล์

- โฟลเดอร์ `<data>\health\` เป็นของ CMD Studio ทั้งหมด `--cleanup` ลบทั้งโฟลเดอร์
- **ป้ายของหน้าต่างหนึ่งหน้าต่าง** ชื่อ `start-<pid>` เนื้อในเป็นข้อความ ASCII บรรทัดเดียว `v1 <unix seconds>` ตอนนับ ใช้เวลาจากเนื้อในไฟล์เท่านั้น ไม่ใช้เวลาแก้ไขไฟล์
- **`paused.json`:**
  ```json
  { "version": 1, "reason": "cmdStarts" | "clinkCrash" | "recovery" | "user",
    "at": <unix ms>, "count": <จำนวนครั้งที่นับได้>, "by": "clink" | "app",
    "resume": null | { "themeId": "...", "target": "all" | "wt" } }
  ```
  `resume` มีค่าเมื่อแอปหยุดธีมด้วย `revert_all` (§4.2) Lua เขียนแค่ 4 field แรกพร้อม `"by": "clink"` เท่านั้น
- ค่าคงที่ 2 ตัวมีที่เดียวใน Rust แล้วตัวสร้างเขียนลง Lua:
  - `STALE_AFTER = 60` วินาที
  - `PAUSE_AFTER = 3` ครั้ง

### 3.2 ลำดับใน `init.lua`

ทุกขั้นห่อด้วย `pcall` ข้อผิดพลาดของไฟล์ใดๆ ทำให้ข้ามตัวนับไปเฉยๆ ห้ามหยุดธีมเพราะอ่านหรือเขียนไฟล์ไม่ได้ ห้าม raise และห้ามพิมพ์อะไร ยกเว้นบรรทัดใน §3.3

1. ถ้ามี `paused.json`: ไม่โหลด OMP, ตั้งตัวแปร global `CMDSTUDIO_PAUSED = true` ให้ `banner.lua` เห็น, พิมพ์บรรทัดแจ้งของ §3.3 แล้วจบ
2. นับป้าย `start-*` ที่เวลาในไฟล์เก่ากว่าเวลาตอนนี้เกิน `STALE_AFTER` ถ้าได้ตั้งแต่ `PAUSE_AFTER` ขึ้นไป:
   - เขียน `paused.json` (`reason: "cmdStarts"`, `by: "clink"`, `count`)
   - ลบป้ายทั้งหมด
   - ทำต่อตามข้อ 1
3. เขียนป้ายของตัวเอง `start-<pid>`
4. โหลด OMP ตามเดิม
5. ตอนถึง prompt แรก ตามจุดที่ spike ใน §0 ยืนยัน (หลัง prompt filter ของ OMP คืนค่า): ลบป้ายของตัวเอง และลบป้ายเก่าทั้งหมดที่เลย `STALE_AFTER` แล้ว เปิดสำเร็จครั้งเดียวจึงเริ่มนับใหม่ ตัวนับจึงหมายถึง "ติดกัน"
   - ป้ายของหน้าต่างอื่นที่ยังไม่ถึง `STALE_AFTER` ห้ามลบ เพราะ WT เปิดหลายแท็บพร้อมกันได้

### 3.3 สิ่งที่ผู้ใช้เห็นใน cmd

- `banner.lua` ไม่พิมพ์กล่องต้อนรับเมื่อ `CMDSTUDIO_PAUSED` เป็นจริง
- **บรรทัดเดียว ภาษาอังกฤษ สีปกติของหน้าต่าง:** "CMD Studio paused its theme because cmd failed to start 3 times. Open CMD Studio to turn it back on." ตัวเลขมาจาก `count` หน้าต่างต่อไปที่ยังหยุดอยู่ใช้บรรทัดสั้นกว่า "CMD Studio's theme is paused. Open CMD Studio to turn it back on."
- prompt เป็นของ cmd ตามเดิม Clink ยัง inject อยู่ จึงยังมี history และการเติมคำของ Clink

### 3.4 สิ่งที่ตัวนับไม่ครอบ

- **cmd แครชตอน inject ก่อน Lua จะทำงาน:** ใช้ §4.3 กับ §4.4
- **OMP ช้าที่ prompt หลังจากเปิดสำเร็จแล้ว:** ไม่อยู่ในขอบเขต (ดู §11)
- **ผู้ใช้ปิดหน้าต่างก่อน prompt ขึ้น:** นับเป็นหนึ่งครั้ง ยอมรับได้ เพราะต้องเกิดติดกัน 3 ครั้ง และปุ่ม "เปิดธีมกลับ" ใช้คลิกเดียว

## §4 ฝั่งแอป: หยุดธีมและเปิดกลับ

### 4.1 สองระดับของการหยุด

| ระดับ | ใครหยุด | เครื่องเปลี่ยนไหม | เปิดกลับด้วย |
|---|---|---|---|
| หยุดใน cmd (`by: "clink"`) | `init.lua` (§3) | ไม่ AutoRun และ Clink อยู่ครบ | "เปิดธีมกลับ" ลบ `paused.json` และป้าย ไม่ต้องใช้ทรานแซกชัน |
| หยุดระดับเครื่อง (`by: "app"`) | แอป (§4.3, §4.4, ปุ่มหยุดธีม) | ใช่ ทำ `revert_all` ซึ่งเป็นทรานแซกชันที่มี journal | "เปิดธีมกลับ" ใช้ธีมใน `resume` ซ้ำผ่าน `plan_apply` และ ApplyFlow (R7) แล้วลบ `paused.json` ตอน commit |

- ถ้า `revert_all` ไม่จบดี (ย้อนไม่ครบ หรือ `E_BUSY`) ให้รายงานแบบเดิมของ §5.5 และยังเขียน `paused.json` เพื่อให้หน้าแรกบอกสถานะได้
- ถ้า `resume` ชี้ไปที่ธีมที่ถูกลบไปแล้ว ปุ่ม "เปิดธีมกลับ" จะพาไปหน้าธีมแทน

### 4.2 สิ่งที่หน้าแรกแสดง

- **แถบเตือนบนหน้าแรก** (สองภาษา) แสดงเมื่อมี `paused.json`:
  - บอกเหตุผล: cmd เปิดไม่ถึงพร้อมท์ N ครั้งติด / cmd แครชใน Clink N ครั้ง / หยุดจากทางลัด Recovery / ผู้ใช้หยุดเอง
  - บอกเวลา
  - ปุ่ม "เปิดธีมกลับ", "ย้อนทุกอย่าง" (เฉพาะระดับ clink) และ "แจ้งปัญหา"
- **ปุ่ม "หยุดธีม"** ในหน้าแรก ใต้ธีมที่ใช้อยู่ ทำการหยุดระดับเครื่อง (`reason: "user"`) และมีกล่องยืนยันที่บอกว่าเปิดกลับได้

### 4.3 ตรวจ event log ทุกครั้งที่เปิดแอป

- ทำในเบื้องหลังหลังหน้าแรกขึ้นแล้ว ไม่หน่วงการเปิดแอป และข้ามเมื่ออยู่ในโหมดกู้คืน
- **ช่วงเวลาที่อ่าน:** Application log, provider "Application Error", event ID 1000 นับตั้งแต่ commit การใช้ธีมครั้งล่าสุด (§0) และไม่เก่ากว่า 7 วัน
- **นับเหตุการณ์ที่:** ชื่อแอปที่แครชเป็น `cmd.exe` และชื่อโมดูลที่แครชขึ้นต้นด้วย `clink_dll` (ไม่สนตัวพิมพ์เล็กใหญ่) อ่านจาก EventData ที่ spike ยืนยัน ห้ามอ่านข้อความที่แปลภาษาแล้ว
- **ถ้าได้ตั้งแต่ 3 ครั้งขึ้นไป** มีธีมใช้อยู่ และยังไม่ได้หยุดระดับเครื่อง: หยุดระดับเครื่องให้อัตโนมัติ (`reason: "clinkCrash"`, `count`) เขียน log แล้วแสดงแถบของ §4.2
  - การหยุดใน cmd ไม่นับเป็นการหยุดในข้อนี้ เพราะ Clink ยัง inject อยู่ แครชใน DLL จึงยังเกิดได้ ถ้ามีการหยุดใน cmd อยู่แล้ว ให้เขียน `paused.json` ทับด้วยของระดับเครื่อง
- **ถ้าอ่าน event log ไม่ได้** (ปิดอยู่, ไม่มีสิทธิ์, ช้าเกิน 5 วินาที): ไม่ทำอะไร เขียน log บรรทัดเดียว ห้ามหยุดธีมเพราะอ่านไม่ได้
- adapter ใหม่ `EventLog` ใน core มีตัวจริงที่ใช้ Windows Event Log API (`EvtQuery` และ `EvtRender` แบบ XML) และตัวปลอมสำหรับเทสต์

### 4.4 ทางลัด "CMD Studio Recovery"

- ตัวติดตั้งของ phase 4 สร้างไว้ในเมนู Start คู่กับทางลัดของแอป (§6 ของสเปกหลัก) โดยเรียก `cmdstudio.exe --recovery`
- **`--recovery` เปิดแอป ไม่ใช่ CLI** `main.rs` ต้องแยกกรณีนี้ก่อนส่งให้ CLI แล้วทำตามลำดับ:
  1. ย้อนทรานแซกชันที่ค้างอยู่ เพราะเป็นคำสั่งที่เปลี่ยนเครื่องตามปกติของ §5.5
  2. ถ้ามีธีมใช้อยู่และยังไม่ได้หยุดระดับเครื่อง ให้หยุดระดับเครื่อง (`reason: "recovery"`)
  3. เปิดแอปในโหมดกู้คืน (§5.2)
- **ถ้าแอปเปิดอยู่แล้ว:** callback ของ single-instance รับ argument `--recovery` แล้วให้ตัวที่เปิดอยู่ทำขั้น 1-2 จากนั้นสลับไปหน้าโหมดกู้คืน
- **ถ้าเปิดหน้าต่างไม่ได้:** ขั้น 1-2 ยังเกิดขึ้น แล้วกล่องข้อความของ §5.4 บอกผล
- หน้าช่วยเหลือมีย่อหน้าสั้นสองภาษา: "ถ้า cmd เปิดไม่ขึ้น: เปิดเมนู Start แล้วเลือก CMD Studio Recovery"

### 4.5 ตรวจสุขภาพ D10 (อ่านอย่างเดียว)

| สถานะ | เมื่อไหร่ | ปุ่มแก้ |
|---|---|---|
| `ok` | ไม่ได้หยุด และไม่มี cmd แครชใน Clink ตั้งแต่ใช้ธีม | — |
| `warn` | หยุดอยู่ บอกระดับ เหตุผล และเวลา | "เปิดธีมกลับ" |
| `warn` | cmd แครชใน Clink 1-2 ครั้ง | "หยุดธีม" |
| `fail` | cmd แครชตั้งแต่ 3 ครั้งขึ้นไป แต่ธีมยังเปิดอยู่ | "หยุดธีม" |
| `skipped` | อ่าน event log ไม่ได้ บอกเหตุผล | — |

การแก้ทุกข้อผ่านแผนเดียวกับการใช้ธีม เหมือน doctor ข้ออื่น (§5.8)

## §5 แอปเปิดไม่ขึ้น แครชซ้ำ และแครชที่ไม่คาดคิด

### 5.1 บันทึกการเปิดแอป `<data>\run.json`

```json
{ "version": 1, "pid": 1234, "createdAt": <เวลาสร้างโปรเซส จาก GetProcessTimes>,
  "startedAt": <unix ms>, "uiReadyAt": null | <unix ms>, "failedStarts": 0, "safeMode": false }
```

- เขียนตอนเริ่ม ก่อนสร้างหน้าต่าง ด้วย `write_atomic`
- UI เรียก `app_ready` หลังวาดหน้าแรกครั้งแรก ตัวแอปจึงบันทึก `uiReadyAt` และตั้ง `failedStarts = 0`
- ปิดแอปตามปกติ (ปิดหน้าต่าง หรือ event ออกจากแอปของ Tauri) จะลบไฟล์นี้
- **ตอนเริ่ม ถ้ามีไฟล์ของครั้งก่อน:**
  - ถ้า pid นั้นยังมีชีวิตและ `createdAt` ตรงกัน แปลว่ายังเปิดอยู่จริง เคสนี้ single-instance จัดการไปแล้ว จึงไม่ควรเกิด ถ้าเกิดให้ข้ามไป
  - ถ้าไม่ใช่ แปลว่าครั้งก่อนปิดไม่ปกติ ถ้า `uiReadyAt` เป็น `null` ให้ `failedStarts` ของครั้งนี้เป็นของครั้งก่อนบวก 1 ถ้าไม่ใช่ ให้แสดงประกาศของ §5.3
- **pid ใช้ซ้ำได้บน Windows** จึงต้องเทียบ `createdAt` ทุกครั้ง
- ถ้าอ่านหรือเขียนไฟล์นี้ไม่ได้ แอปยังเปิดได้ตามปกติ และเขียน log บรรทัดเดียว

### 5.2 โหมดกู้คืน (safe mode)

- **เข้าเมื่อ:** `failedStarts` ตั้งแต่ 2 ขึ้นไป หรือเปิดด้วย `--recovery`
- **สิ่งที่ไม่ทำ:**
  - ไม่โหลดคลังธีม ร่าง พรีวิว หรือการสลับธีมเร็ว
  - ใช้ค่าตั้งต้นของการตั้งค่าในหน่วยความจำ โดยไม่เขียนทับ `settings.json`
  - ภาษาใช้ค่าใน `settings.json` ถ้าอ่านได้ ไม่ได้ก็ใช้อังกฤษ
- **หน้าเดียว "โหมดกู้คืน"** (สองภาษา) บอกว่าทำไมถึงอยู่ในโหมดนี้ แล้วมี:
  - สถานะการหยุดธีม พร้อม "เปิดธีมกลับ"
  - "ย้อนทุกอย่าง"
  - "จุดย้อนกลับ" (รายการเดียวกับหน้าช่วยเหลือ)
  - "ตรวจสุขภาพ"
  - "เปิดโฟลเดอร์ log"
  - "แจ้งปัญหา"
  - "รีเซ็ตการตั้งค่าของแอป" ย้าย `settings.json` ไปเป็น `settings.json.reset-<ms>` แล้วใช้ค่าตั้งต้น
  - "เริ่มแบบปกติ" ออกจากโหมดกู้คืน แล้วโหลดหน้าแอปใหม่
- phase 4 เพิ่มช่อง "อัปเดตตอนนี้" ไว้ในหน้านี้ เพราะเวอร์ชันใหม่อาจแก้สาเหตุที่แครชได้ หน้านี้จึงเว้นที่ไว้ให้เหมือนที่หน้าแรกเว้นไว้

### 5.3 บันทึกแครชและการแจ้งครั้งต่อไป

- **panic hook** ตั้งตอนเริ่มทั้งแอปและ CLI แล้วเขียน `<data>\logs\crash-<unix ms>.txt` (UTF-8) ซึ่งมี:
  - เวอร์ชัน, เวลา, ชื่อ thread, ข้อความของ panic, ตำแหน่ง และ backtrace (`Backtrace::force_capture`)
  - ทุกบรรทัดผ่าน `redact` และ `redact_sids` ก่อนเขียน
  - เก็บไว้ 10 ไฟล์ล่าสุด
  - hook ห้าม panic ซ้ำ และห้ามล้มเพราะเขียนไม่ได้ เขียนเสร็จแล้วเรียก hook เดิมต่อ
- **แครชแบบ native** (เช่นใน WebView2) panic hook ไม่เห็น `run.json` อย่างเดียวที่บอกได้ ประกาศจึงไม่มีไฟล์แครชแนบ
- **ประกาศครั้งต่อไป** อยู่ใน `StartNotices` สองภาษา: "CMD Studio ปิดไปแบบไม่ปกติเมื่อ <เวลา>" พร้อมปุ่ม "แจ้งปัญหา" และ "ปิด"
  - "แจ้งปัญหา" ไปแท็บแจ้งปัญหาของหน้าช่วยเหลือ ซึ่งแนบเนื้อหาของบันทึกแครชล่าสุดต่อท้ายข้อมูลวินิจฉัย
  - ผู้ใช้เห็นทุกอย่างก่อนคัดลอกและเปิด GitHub Issues ไม่มีการส่งเองอัตโนมัติ
  - "ปิด" จดว่าแจ้งไปแล้วสำหรับแครชครั้งนั้น

### 5.4 เปิดหน้าต่างไม่ได้

- `console::fatal` ของกรณี `window_failed` เปลี่ยนเป็นกล่อง Yes/No (`MB_YESNO`) ข้อความ:
  > CMD Studio could not open its window: `<why>`. Your themes are safe. Undo everything CMD Studio changed on this computer (cmd, Windows Terminal, fonts)? The log is in `<logs path>`.
- **Yes:** ทำ `revert_all` ผ่าน backend ภายใต้ล็อกตามปกติ แล้วแสดงกล่องที่สองบอกผล (สำเร็จ / ย้อนไม่ครบ ให้ดูขั้นตอนใน log / `E_BUSY`)
- **No:** จบตามเดิม
- **กรณี `start_failed`** (ยังไม่มีโฟลเดอร์ข้อมูล เช่นไม่มี LOCALAPPDATA) ย้อนอะไรไม่ได้ จึงคงกล่องข้อความแบบเดิม

## §6 แอปค้างระหว่างใช้

### 6.1 แถบ "ยังทำงานอยู่"

- ตัวห่อ `Ipc` นับทุกคำสั่งที่รออยู่ ถ้ารอเกิน 10 วินาที จะขึ้นแถบบนสุดของหน้า (สองภาษา): "CMD Studio is still working: <ชื่องาน>…"
- ชื่องานมาจากพจนานุกรม และแถบอยู่ในบริเวณ `role="status"`

### 6.2 เส้นตายของคำสั่งอ่านอย่างเดียว

- คำสั่งที่ไม่เปลี่ยนเครื่องมีเส้นตาย 60 วินาที รายการคำสั่งเหล่านี้กำหนดไว้ที่เดียวและมีเทสต์ตรวจว่าครบ
- ถ้าเลยเส้นตาย UI จะ reject ด้วยรหัสใหม่ `E_TIMEOUT` (เพิ่มใน §5.9 ของสเปกหลัก) พร้อมปุ่มลองใหม่ คำตอบที่มาช้ากว่านั้นถูกทิ้งด้วยตัวนับลำดับแบบเดียวกับของ editor
  - `error.rs` มีเทสต์ที่เทียบตาราง `MEANINGS` กับแถวของ §5.9 ทุกแถว จึงต้องเพิ่ม `E_TIMEOUT` ทั้งในสเปกและใน `MEANINGS` ใน commit เดียวกัน แม้ว่ารหัสนี้จะเกิดฝั่ง UI ก็ตาม

### 6.3 คำสั่งที่เปลี่ยนเครื่อง

- ยกเลิกกลางทางไม่ได้ เพราะทรานแซกชันต้องจบ (§5.5)
- **ถ้าเกิน 3 นาที** แถบจะเพิ่มปุ่ม "เริ่ม CMD Studio ใหม่" ซึ่งมีกล่องยืนยันว่า "การเปลี่ยนแปลงที่ยังไม่เสร็จจะถูกย้อนกลับตอนเริ่มใหม่"
  - กดแล้วเรียก IPC `app_restart` ซึ่งเริ่มโปรเซสใหม่ ทรานแซกชันที่ค้างจะถูกย้อนที่คำสั่งถัดไปตาม journal ที่มีอยู่แล้ว
  - ห้ามมีทางอื่นที่ฆ่าทรานแซกชันโดยไม่ผ่าน journal
- **หลังหน้าแอปโหลดใหม่ทุกกรณี** (Reload, §6.4) UI ถาม IPC `app_status` ก่อน ถ้า backend ของโปรเซสนี้ยังทำคำสั่งที่เปลี่ยนเครื่องอยู่ ให้แสดง "กำลังใช้ธีมอยู่ รอให้เสร็จก่อน" แล้วรอจนจบ จากนั้นจึงอ่านสถานะใหม่

### 6.4 WebView2 ล้ม

- ฟัง `ProcessFailed` ถ้า renderer ล้มหรือไม่ตอบสนอง ให้โหลดหน้าใหม่เอง
- ถ้าเกิด 3 ครั้งภายใน 1 นาที ให้หยุดโหลดใหม่แล้วใช้กล่อง Yes/No ของ §5.4
- ข้อนี้ทำเมื่อ spike ใน §0 ยืนยันว่าเข้าถึงได้เท่านั้น

### 6.5 ตัวจับรวมใน UI

- `window.onerror` และ `unhandledrejection` แสดงประกาศ `E_INTERNAL` (ใช้ `CrashNotice` ตัวเดียวกัน พร้อม Reload)
- ส่งรายละเอียดไปเขียน log ผ่าน IPC `log_ui_error` ซึ่งผ่าน `redact` และรับไม่เกิน 20 ครั้งต่อการเปิดแอปหนึ่งครั้ง

## §7 ไฟล์ใหม่ในโฟลเดอร์ข้อมูล (§5.3)

|---|---|---|
| `health\start-<pid>` | `init.lua` | `init.lua` เมื่อเปิดสำเร็จ หรือเมื่อหยุดธีม, "เปิดธีมกลับ", `--cleanup` |

### CLI

`cmdstudio.exe --recovery` เปิดแอป (§4.4) ส่วนคำสั่ง CLI อื่นเหมือนเดิม

## §9 ภาษาและการเข้าถึง

- ข้อความใหม่ใน UI มีครบทั้ง en และ th ตามธรรมเนียมใน `th.ts`: พร้อมท์, เวอร์ชัน, "CMD Studio", จุดย้อนกลับ, ไม่ใช้ "สำรอง"
- สิ่งที่เขียนลง cmd และกล่องข้อความของ Windows เป็นภาษาอังกฤษ
- หน้าโหมดกู้คืน แถบหยุดธีม แถบยังทำงานอยู่ และประกาศแครช อยู่ในการกวาดชื่อปุ่มทั้งสองภาษา (phase 3) และหัวข้อของหน้าโหมดกู้คืนรับ focus

## §10 การทดสอบ

- **Lua ใน `init.lua` และ `banner.lua`:** รันจริงด้วย `mlua` ในเทสต์ของ core โดยใช้ `clink`, `os` และ `io` ปลอมที่ชี้ไปโฟลเดอร์ชั่วคราว กรณีที่ต้องมี:
  - เปิดครั้งแรก
  - เปิดสำเร็จแล้วป้ายถูกลบ

## §12 ลำดับงานที่เสนอ (แผนจริงเขียนด้วย writing-plans)

## §13 สิ่งที่ปรับหลังเขียนแผน 3b-1 (2026-10-17)

ตอนเขียนแผน `docs/superpowers/plans/2026-10-17-phase3b-1-recovery-cmd.md` พบว่าบางข้อในเอกสารนี้ไม่ตรงกับโค้ดที่มีอยู่ จึงปรับตามนี้ เจตนาของทุกข้อยังเหมือนเดิม

- **D10 เปลี่ยนเป็น D12** เพราะ D10 เป็นข้อตรวจแอปแบบแพ็กมาตั้งแต่ phase 1b (`doctor.rs`) ส่วน D12 มีรหัสใหม่ 2 รหัสใน §5.9 ของสเปกหลัก คือ `E_THEME_PAUSED` และ `E_CMD_CRASHED` เพราะทุกข้อตรวจที่เป็น `warn` หรือ `fail` ต้องมีรหัส
- **ตัวนับนับเฉพาะหน้าต่าง cmd จริง** การตรวจหลังใช้ธีม (`clink set` ใน `verify.rs`) และการตรวจสุขภาพ D3 ก็โหลด `init.lua` ด้วย ถ้าเขียนป้ายทุกครั้ง แค่เปิดหน้าแรก 3 ครั้งธีมก็จะถูกหยุด ป้ายจึงเขียนเฉพาะเมื่อ Clink ทำงานอยู่ใน cmd.exe (`os.gethost`)
- **จุดที่นับว่าถึงพร้อมท์แรก** `clink.onbeginedit` ทำงานก่อน prompt filter (เคยวัดไว้ใน `spikes/vm/guest/proto-setup.ps1`) จึงใช้ prompt filter ของ CMD Studio เองที่ทำงานหลังของ OMP แทน spike ใน §0 จะยืนยันอีกครั้ง
- **ข้อ 1 ของ §1 นับเฉพาะกรณีที่ไปไม่ถึงพร้อมท์** ถ้า OMP แครชหรือ Lua error แต่ cmd ยังขึ้นพร้อมท์ที่ใช้ได้ (`init.lua` เดิมจัดการไว้แล้ว) ไม่นับเป็นครั้งที่พัง เพราะ cmd ยังใช้งานได้ ที่นับคือ OMP ค้าง และ cmd ตายก่อนถึงพร้อมท์
- **"ย้อนทุกอย่าง" ของแอปยกเลิกการหยุดใน cmd ด้วย** ถ้าไม่ยกเลิก `paused.json` จะค้างอยู่หลังย้อนทุกอย่าง แต่การหยุดระดับเครื่องที่แอปตั้งไว้ยังอยู่จนผู้ใช้กด "เปิดธีมกลับ" และการใช้ธีมที่ commit แล้วทุกครั้ง รวมถึง `cmdstudio apply`, ยกเลิกการหยุดทุกแบบ
- **ไม่มี event ใหม่** §5.7 ของสเปกหลักมีแค่ `apply-progress` ดังนั้น `recovery_status` จะรอผลการตรวจ event log ตอนเริ่มได้นานสุด 30 วินาทีแทน และหน้าแรกจะอ่านใหม่หนึ่งครั้งเมื่อการตรวจนั้นหยุดธีมไประหว่างที่หน้าแรกกำลังอ่าน
- **ทางลัด Recovery และ `--recovery` อยู่ใน 3b-2** เพราะตอนนี้ `main.rs` ถือว่าทุก argument เป็น CLI ใน 3b-1 ข้อ 2 ของ §1 จึงอาศัยการเปิดแอปอย่างเดียว ย่อหน้า "ถ้า cmd เปิดไม่ขึ้น" ในหน้าช่วยเหลือของ 3b-1 จึงบอกให้เปิด CMD Studio ส่วน 3b-2 เพิ่มทางลัดเข้าไป
- **"ตั้งแต่ใช้ธีมครั้งล่าสุด"** ใช้ `applied_at_ms` ใน `state.json` ซึ่งบันทึกตอนเตรียมใช้ธีม ก่อน commit เล็กน้อย
- **เทสต์ Lua ใช้ไฟล์ในหน่วยความจำ** `io.open` ของ mlua เป็น `fopen` แบบ ANSI จึงทดสอบ path ไทยไม่ได้ เรื่อง path ไทยจึงพิสูจน์ใน spike (S2) และบน VM-C แทน
