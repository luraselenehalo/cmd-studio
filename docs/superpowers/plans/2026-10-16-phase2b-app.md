# Phase 2b — The CMD Studio App: Implementation Plan (index)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This file is the index: read it first, then the three sub-plans in order. Each sub-plan carries the full Global Constraints, its own Review Focus and complete code in every step, so a task can be executed from the sub-plan alone.

**Goal:** Ship the CMD Studio desktop app — the Tauri 2 shell over `cmdstudio-core`, its IPC, the theme library with drafts, import and export, the ts-rs bindings, the React UI (first-run wizard, home, themes and editor, after-apply bar, settings, help with doctor, restore points, revert, problem report, guide and credits, advanced), Thai and English with English as the default, accessibility, the CI app job — so that a person on a fresh Windows 11 gets a themed cmd in five clicks and can undo it (spec §1 criterion 1).

**Architecture:** One exe, `cmdstudio.exe`: started bare it opens the Tauri window; with arguments it runs the Phase 1b CLI (`cmdstudio_cli::run`, now a library). Behind the window a `Backend<M: Machine>` (`app/src-tauri/src/backend`) holds one method per IPC command, written over the core's `System` of adapters so every command is tested against the core's `FakeMachine` and never against this computer; the 27 `#[tauri::command]`s in `ipc.rs` only move arguments and results across, run the backend on a blocking thread, log one line per call and turn every error into `AppError {code, messageTh, messageEn, details}`. The core gains three small things the app needs: a `ts` feature that exports its public types with ts-rs, `Paths` for the app's folders plus an `autorun_summary`, and `run_apply_with`, which reports each step of an apply so the UI can show progress. The UI (`app/ui`, React 19 + Vite 8 + TypeScript, no router or state library) consumes the bindings through one `Ipc` interface with two implementations — Tauri's `invoke` and an in-memory mock for the tests and the visual check — and paints the preview spans the core draws: no palette, contrast or prompt logic in TypeScript.

**Tech Stack:** Rust 1.99.0; `tauri = "=2.12.4"` (`tauri-build 2.7.3`, `tauri-utils 2.10.2`, wry 0.57.0, WebView2), `tauri-plugin-single-instance = "=2.5.4"`, `ts-rs = "=12.0.1"`, `rfd = "=0.17.2"` (native file dialogs, `default-features = false`), `windows-sys = "=0.61.2"`, `sha2 0.11`, serde/serde_json/thiserror/uuid as the core. Node 24.21.0, `@tauri-apps/api 2.12.4`, `@tauri-apps/cli 2.12.3`, `react 19.3.1`, `vite 8.3.4`, `typescript 5.9.3`, `vitest 5.0.5`, `jsdom 30.1.3`, `@testing-library/react 16.3.3`, `@testing-library/user-event 14.6.8`, `@vitejs/plugin-react 6.1.2`, `@types/react 19.3.0`, `@types/react-dom 19.3.0`, `@types/node 24.19.2`. Every version is exact in the manifests and locked in `Cargo.lock` / `app/package-lock.json`.

**Spec:** `docs/superpowers/specs/2026-10-10-cmd-studio-design.md` (Thai; binding): §1, §2.1, §3, §4, §5.1, §5.3, §5.6, §5.7, §5.9, §5.10, §6.6, §7, §8, appendix B — as the working copy on the branch has it, with the coordinator's uncommitted edits of 2026-10-16. ## Why three sub-plans, and their order

The work is 60 files and about 11,000 lines of new code and tests, which no reviewer can hold as one gate. It splits along the spec's own phases (§8: "2 หน้าจอธีม", "3 วิซาร์ดและหน้าอื่น") into three plans, each ending in software that runs and is tested on its own:

1. **`2026-10-16-phase2b-shell.md` — the Rust side** (16 tasks). The core's `ts` feature and the three additions, the CLI as a library, the app crate with every backend command tested over the fake machine, the IPC layer, the capability and CSP, the bindings export, the Rust part of the CI app job, and the spec's §5.3/§5.7/§5.9 edits. Ends with `cargo test -p cmdstudio-app` green (97 tests) and 71 binding files committed. No UI yet: `build.rs` writes a placeholder page so the crate builds without Node.
2. **`2026-10-16-phase2c-themes-ui.md` — the themes UI** (7 tasks). The Node toolchain and lockfile, both dictionaries with their completeness test, the `Ipc` interface with the Tauri and mock implementations, the shared components (preview, notices, dialog, theme card, the apply flow), the editor's reducer, the Themes and Editor screens, a shell that shows them, the visual check in the browser pane, and the full CI app job. Ends with the library and editor usable against the mock (vitest 20 tests) and the Tauri build on CI.
3. **`2026-10-16-phase3-wizard-home-help.md` — the wizard and the other pages** (4 tasks). Wizard, Home, Settings, Help (doctor, restore points, revert all, report a problem, guide, credits), Advanced, the final shell, the whole-app tests including the five-click criterion and the two-language accessibility sweep, appendix B rows, and the VM check protocol for spec §1 criterion 1. Ends with vitest 32 tests and the controller's VM checklist.

Execute them in this order; each later plan's first task names what it needs from the earlier ones. The shell plan's Tasks 1–4 touch the core and the CLI and are the only tasks of this phase that change code Phase 1–2a shipped.

## Decisions this plan takes

The architect's, made where the spec and the brief are silent; the founder may change any of them. Each says what, why, and what it costs if wrong.

1. **One Windows-subsystem exe.** `cmdstudio.exe` is built with `windows_subsystem = "windows"` in release so no console flashes when the app opens; in CLI mode it attaches to the parent console first (`AttachConsole(ATTACH_PARENT_PROCESS)`). Why: spec §5.7 says the CLI is the same exe, and a console-subsystem app would open a black window behind the UI. Cost if wrong: cmd does not wait for a Windows-subsystem program, so `cmdstudio doctor` typed in cmd prints after the prompt came back (`cmdstudio doctor | more` and `start /wait` wait; the uninstaller's `ExecWait` and the tests, which call the library, wait). Open question 1 asks the founder whether that is acceptable or Phase 4 should ship a second console exe.
2. **`Backend<M: Machine>` over the core's `System`.** One trait with one method (`fn system(&self) -> System<'_>`), implemented by `RealMachine` (the Windows adapters) and, in tests, by the core's `FakeMachine`. Why: every command is then tested end to end against the in-memory machine, the only way to meet the test-safety rule and still test the app. Cost if wrong: a generic parameter the IPC layer must name (`State<'_, Arc<Backend<RealMachine>>>`); nothing functional.
3. **A plan digest instead of holding the lock across the UI.** `plan_apply` prepares the plan, lets the lock go and returns it with `digest = sha256(summary_en, warnings, steps)`; `apply(request, digest)` prepares again under the lock and applies only if the digest is the same, otherwise answers `status: planChanged` with the new plan, which the UI shows again and never applies on its own. Why: a user may read the plan for minutes; the lock (spec §5.5) must not be held that long, and the plan must be what the user read (spec §2.1 "แสดงรายการ 'สิ่งที่จะเปลี่ยน' ก่อนแตะเครื่องทุกครั้ง"). Cost if wrong: a plan that changed between show and apply is caught by the digest; a digest too strict only makes the user press Apply once more.
4. **Settings in `settings.json`, not in `state.json`.** `{version: 1, language, target, setWtDefaultProfile, updates, wizardDone}`, defaults `en / all / true / auto / false`; a damaged or newer file is set aside as `settings.json.damaged-<ms>`, the defaults are used, and the UI is told (`SettingsLoad.resetFrom`). Why: `undo` restores `state.json` byte for byte (Phase 1b), which would roll a language choice back with the theme; spec §5.3's tree says state.json holds "settings" and the shell plan's Task 16 corrects it. Cost if wrong: one more file for `--cleanup` to know (Task 4 teaches it).
5. **WebView2's data folder is `<data>\webview`.** The window is declared in `tauri.conf.json` with `create: false` and built in `setup` with `WebviewWindowBuilder::from_config(..).data_directory(paths.webview())`. Why: Tauri's default puts WebView2's `EBWebView\` directly in the data folder, which `--cleanup` would refuse as "not CMD Studio's"; a folder of our choosing is listed in `put_there_by_cmd_studio` (controller carry). Cost if wrong: WebView2 writes elsewhere and `--cleanup --data-dir` refuses the folder; the CLI test of Task 4 and the VM check catch it.
6. **Progress comes from the core.** `actions::run_apply_with(sys, ctx, prepared, &mut dyn FnMut(Progress))` wraps the transaction's executor and verifier and tells `BackingUp {step, total}`, `Applying {step, total, op}`, `Verifying`, `RollingBack {step, total}`; `run_apply` is unchanged and delegates to it with a no-op listener. The app emits each as an `apply-progress` event `{phase, step, total, kind}`. Why: spec §5.7 names the event; the UI must show real steps, not a spinner. Cost if wrong: a wrong count shows a wrong progress bar; two core tests pin the order and the rollback.
7. **The theme library on disk.** My themes are `themes\<name>.cmdtheme` (the file name is the theme's name made safe and de-duplicated, never the id, so a folder listing reads well); drafts are `drafts\<id>.cmdtheme` and are offered when the theme opens; presets are `presets::builtin()`, never written; Customize copies a preset into my themes as "My <name>" with a new id. Import reads the chosen file once, validates it, keeps the theme in memory under a token and shows a preview; confirm writes it (a taken id gets a new one, a taken name is flagged). Export writes to the path the Save dialog returns, named `<name>.cmdtheme`. Why: spec §3.1 and §3.3. Cost if wrong: a file name clash is handled by de-duplication; a hand-made file that is not a theme is listed as a problem, not a crash (Review Focus 1).
8. **Doctor fixes go through the same apply flow.** `doctor_fix(check_id)` returns a `FixProposal {kind, request, plan}`: `reapply` and `replaceOtherClink` carry an `ApplyRequest` and its plan, which the UI shows and applies exactly like any apply; `installWindowsTerminal` opens the Store, `openNewCmdWindow` opens cmd, `openWindowsTerminalOnce` and `reinstall` are instructions. Why: spec §4.3 "ตรวจสุขภาพพร้อมปุ่มแก้" and §2.1 (every change shown first). Cost if wrong: a fix the doctor cannot offer shows no button, only the text.
9. **Diagnostics redact the user name.** `diagnostics_copy` builds the report (versions, data folder, settings, the applied theme, the doctor's checks, the restore points, the log's last lines) and replaces the user's folder name wherever it appears (any case) with `<you>` before the UI copies it to the clipboard. Why: spec §4.3 "คัดลอกข้อมูลวินิจฉัย" goes to a public GitHub issue. Cost if wrong: a path with the name slips into an issue; three tests pin the redaction.
10. **The log.** `logs\cmdstudio.log`, one line per IPC command (`<UTC time> cmd=<name> ms=<n> ok|err=<code>`), rotated at 1 MB keeping 5 files (spec §5.3). The Advanced page shows its tail. No theme content, no paths of the user's files in it.
11. **The UI's plumbing is in-house.** A `Route` union in React state (`router.tsx`), typed dictionaries with `t(key, vars)` (`i18n/`), one `Ipc` interface (`ipc/types.ts`) with `tauri.ts` and `mock.ts`, and an `AppState` context for the settings, the last apply and a reload counter. Why: the brief says no routing library; the app has seven routes. Cost if wrong: none the user sees; a later route is one more union member.
12. **The CSP keeps `style-src 'self'`.** React sets inline styles through the CSSOM (`element.style.color = …`), which a CSP without `'unsafe-inline'` allows; Tauri adds nonces for the scripts and styles it injects. Cost if wrong: the preview's colors would not show in the real window; the phase 3 plan's VM check looks for a CSP violation in the WebView2 console before anything else.
13. **Updates: stored and shown, not performed.** `AppSettings.updates` is `auto | notify | off`, default `auto` (founder 2026-10-16); the Settings page shows the three with a note that the app checks on every launch; the Home page reserves a slot (`data-slot="update-notice"`) for Phase 4's "Updated to vX" notice; no updater plugin, no public key, no `latest.json` in this phase. Cost if wrong: Phase 4 renames a field; the Rust and UI tests pin the default.
14. **`Cargo.lock` is what cargo resolves on the executor's machine.** Every direct dependency is pinned exactly, so the result differs from the plan's scratch lock only in transitive crates that released a compatible version since 2026-10-16; appendix A of the shell plan lists the 381 `[[package]]` entries the plan was verified with, for comparison. `app/package-lock.json`, by contrast, is written verbatim from the 2c plan's appendix, so `npm ci` installs exactly what was tested.
15. **Two tests moved to where their dependency lives.** `the_advanced_page_reads_the_generated_files_after_an_apply` (about `advanced_read` in `backend/mod.rs`) and `the_applied_theme_is_marked_in_use` (about `library.rs`) both apply a theme first, so they sit in `backend/apply.rs`'s tests; that lets `mod.rs` and `library.rs` compile and pass before `apply.rs` exists (shell plan Tasks 8 and 10).

## Review Focus

The five kinds of input or failure the spec implies but states no requirement for, most likely to bite a person using the app, most likely first. Each is pinned by a test in the task that owns the code (the sub-plan and task are named).

1. **A file in `themes\` that is not a theme, or a theme that no longer validates** (hand-edited, copied from an old version, a stray `.txt`). The library must list every good theme and name the bad file with its reason, not fail the page. Pinned in shell Task 10: `files_that_are_not_themes_are_problems_not_themes`, `a_theme_that_does_not_validate_is_refused_with_its_field`; the UI shows `Library.problems` (2c Task 6).
2. **The plan changed between showing it and pressing Apply** (another CMD Studio applied meanwhile, Windows Terminal was installed, the font appeared). It must not be applied; the new plan is shown again. Pinned in shell Task 12: `a_plan_that_changed_since_it_was_shown_is_not_applied`, `the_plan_names_each_step_and_lets_the_lock_go`; the UI's `ApplyFlow` shows the `planChanged` notice (2c Task 4).
3. **Another Clink in AutoRun.** Never replaced silently: `plan_apply` answers `otherClink` with the commands, the UI asks, and only the user's yes sets `replaceOtherClink`. Pinned in shell Task 9 (`another_programs_autorun_and_another_clink_are_told_apart`), Task 12 (`another_clink_is_asked_about_then_turned_off_on_agreement`), 2c Task 6 (`asks about another cmd add-on and goes on with the user's yes`) and phase 3 Task 2 (`asks before replacing another cmd add-on`, in the wizard).
4. **An apply whose check fails** (Oh My Posh exits non-zero, a file does not read back). Everything is rolled back and the user is told so, with the code and a way to copy the details. Pinned in shell Task 3 (`run_apply_with_tells_the_rollback_after_a_failed_check`), Task 12 (`a_failed_check_rolls_back_and_says_why`), 2c Task 6 and phase 3 Task 2 (`… failed apply … put back, with a way to copy the details`).
5. **A damaged or newer `settings.json`** (a crash mid-write, a downgrade). The app must open — in English, with the defaults — set the file aside and say so. Pinned in shell Task 7: `a_damaged_or_newer_file_is_set_aside_and_said`, `a_file_that_cannot_be_read_is_a_read_error`; the shell shows `settings.reset` (phase 3 Task 2).

## Carries to Phase 4

- The Tauri updater: plugin, public key, `latest.json`, the check on every launch, the background download and install in `auto` mode, "notify first", the install moment (before the window, at exit, or on request), never interrupting a transaction (the lock of §5.5), never stealing focus, the "Updated to vX" notice with a link into the Home page's `data-slot="update-notice"` (string `home.update.placeholder`, empty now), offline → carry on silently. It reads `AppSettings.updates` (`auto | notify | off`).
- The installer (NSIS): bundle `active: true`, `resources\` next to the exe, the uninstaller's `cmdstudio --cleanup [--remove-themes]` through `ExecWait`, the ARM64 refusal, open the app at the end; signing through SignPath; winget.
- The daily GitHub Actions workflow that bumps `resources/manifest.json` for Oh My Posh, Clink and Nerd Fonts.
- If the founder wants `cmdstudio doctor` to wait in cmd (open question 1): a second console-subsystem exe in the bundle.
