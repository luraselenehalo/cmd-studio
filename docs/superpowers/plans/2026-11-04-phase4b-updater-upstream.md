# Phase 4b Implementation Plan (outline) — The updater: its code and UI over a fake, the install-moment spike, the key-dependent wiring, the upstream-watch workflow, and the update VM check

> **For agentic workers:** This is a task outline with its interfaces, test names, spike protocol, decision rules and founder gates fixed; the architect expands each task into full steps (code, commands, Expected lines) before execution, in the style of `2026-11-04-phase4a-installer-cli-release.md`. It is written so that its first four tasks run and pass without the updater key; Task 6 waits for the key, Task 9 for a draft release with updater assets. Steps use checkbox (`- [ ]`) syntax for tracking. Task 1's VM half and Task 9's run are the controller's.

**Goal:** CMD Studio updates itself from GitHub Releases: it checks on every launch, in the mode of `settings.json` (automatic by default, notify first, off), never interrupts a transaction, never steals focus, stays silent offline, always says "Updated to vX" with a link to what changed, and after an update installs the new runtime folder, re-applies the current theme through a transaction and deletes the old runtime when nothing holds it; OMP, Clink and the font move only with the app, through a daily workflow that opens a PR when upstream has a new version; update passes on every tier (spec §8).

**Architecture:** `tauri-plugin-updater` (2.13.x, pinned) is used from Rust only, behind a `Updater` trait the app's `backend/update.rs` drives (`check`, `download`, `install`), with a fake for every test; no JS permission is granted to the window. The state machine is pure: `UpdateMode` × network outcome × lock state → `UpdateState`, exposed by a new read-only IPC `update_status` and driven by `update_install` (the notify-mode button, the Recovery page's "Update now"). Before the installer runs, the app writes `<data>\update.json` (`{from, to, notesUrl}`) and ends its run record; the next start reads it, shows the notice through `app_status.updated`, re-applies the theme if the runtime pins changed, prunes old runtime folders, and deletes the file. The moment of installation is the spike's decision (Task 1): the plan's primary is "at close, silent, no relaunch"; Task 3 is written for it with the two fallbacks named. The release workflow signs the installer with the founder's key and uploads `latest.json`; a daily workflow rewrites `scripts/fetch-resources.ps1`'s pins and opens a PR, never merging, never tagging.

**Tech Stack:** Rust 1.99.0, Tauri 2.12.4, `tauri-plugin-updater` =2.13.2 (G10 lists it; pin the newest 2.13.x at execution and record it), `minisign` through the plugin (the key pair from `tauri signer generate`), ts-rs 12.0.1, React 19.3.1 / Vitest 5.0.5, GitHub Actions (`windows-latest`, `ubuntu-latest`; `gh`, `jq`), PowerShell 5.1 for the upstream script (runs on this PC's shell only in `-WhatIf`/fixture mode), VirtualBox VMs; a `python3 -m http.server` on the host for the spike's and the VM check's `latest.json`.

**Spec:** main spec §2.1 (no silent change), §5.3 (`update.json`, the log lines), §5.5 (the lock), §5.7 (the two commands), §5.10 (the one program run from outside `runtime\`: the signed installer), §6.2 (all of it; the ⬜ install moment), §6.4 (the updater manifest, the upstream-watch workflow), §8; recovery spec §5.2 (the "Update now" line on the Recovery page), §6.3 (the restart's journal rule). Phase 4a's plan is the prerequisite: the installer with its hooks (`$UpdateMode` skips `--cleanup`), the console exe, the Path, `release.yml` to a draft.

**Prerequisite:** 4a merged and its VM check green. Baselines measured at the start of Task 2.

## Global Constraints

All of 4a's (copied at expansion), plus:

- **The modes (spec §6.2, founder 2026-10-16):** `UpdateMode::Auto` (default), `Notify`, `Off`, read from `settings.json` at every launch; a damaged `settings.json` means the defaults (phase 2b), so Auto.
- **Never interrupts a transaction:** the install step runs only after `try_lock` of `<data>\cmdstudio.lock` succeeds (`E_BUSY` postpones it to the next launch, with one log line); the lock is held into the installer's start and released by the process's end.
- **Never steals focus:** no window, dialog or relaunch comes from the updater without the user's click; the installer runs with `/S` (the spike decides whether through `Update::install` or the app's own spawn); the "Updated to vX" notice is a `StartNotices` card on the next start, not a popup.
- **Always says it (spec §2.1):** every completed update shows "Updated to vX" with a link, once, until closed (`update_dismiss` is not needed: the card goes with `update.json`'s deletion after the UI has shown it: `app_ready` deletes it).
- **Offline is silent:** a check that fails (no network, DNS, GitHub 5xx, a bad `latest.json`, a signature mismatch) writes one log line `update check=<reason>` and nothing else; the state is `idle`.
- **Add-ons move with the app only (spec §6.2):** no code path downloads OMP, Clink or a font; the runtime folder comes from `resources\` of the new install, checked against `manifest.json` as today.
- **The one program run from outside `runtime\` (spec §5.10):** the signed installer the plugin verified (minisign, the pubkey in `tauri.conf.json`), from `<data>\updates\<file>` or the plugin's temp file, with `/S`; nothing else.
- **IPC:** 37 + `update_status` + `update_install` = 39 names in `command_names.rs`, the capability, `config_guard.rs`'s count; `app_status` gains `updated: Option<Updated>`; `ExternalTarget` gains `ReleaseNotes { version: String }` whose URL is `https://github.com/luraselenehalo/cmd-studio/releases/tag/v<version>` for a `version` that parses as SemVer and nothing else.
- **Secrets:** agents never read, write, print or echo `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` or `UPSTREAM_WATCH_TOKEN`; workflows reference them as `${{ secrets.NAME }}` only; the spike's ephemeral key is generated inside the CI run and never uploaded.
- **The updater's endpoint** is `https://github.com/luraselenehalo/cmd-studio/releases/latest/download/latest.json`, which GitHub serves from the newest *published, non-pre-release* release; see "The endpoint" under Decisions for what that asks of the founder.
- **Downloads (the brief):** the founder's explicit permission for each `gh run download`; one per check.

## Decisions the founder may change

- **The install moment: at close, silent, no relaunch** (primary; Task 1's spike confirms or picks a fallback). The download happens in the background after `app_ready`; the installer runs when the window closes, if the lock is free; the next start shows the notice. The rejected candidate "before the window" would delay every start by a download. Fallback order in Task 1.
- **The endpoint.** GitHub's `releases/latest/download/latest.json` skips releases flagged "pre-release", so an app checking it would never see a v0.x flagged that way. Decision: **the endpoint is that fixed URL, and from the first release the founder publishes with updater assets on, releases are not flagged pre-release; the title and the notes keep saying "pre-release for testers".** Task 6 drops `--prerelease` from 4a's `release.yml` (the words stay). The alternative, if the founder wants the flag: a second, fixed release tagged `updater` whose one asset `latest.json` the workflow replaces (`gh release upload updater latest.json --clobber`) on every publish, and the endpoint `releases/download/updater/latest.json`; Task 6 names both and builds the one the founder picks.
- **`update.json` in the data folder**, written before the installer starts, read and deleted at the next start; `--cleanup` knows it and `updates\`.
- **The re-apply after an update runs at the next start, in the background, under `busy = "update_reapply"`**, only when a theme is applied and `state.json`'s runtime versions differ from the new pins; the UI shows the busy wait it already has (recovery spec §6.3); its log line `update reapply=ok|<code>`.
- **Old runtime folders are pruned best effort** after a successful re-apply and at every start: every `runtime\omp-*` and `clink-*` (and the ProgramData one) whose version is not the pinned one and that is not in `state.json`; a folder held open (a cmd window still has the DLL) stays until the next start.
- **The upstream-watch PR changes `scripts/fetch-resources.ps1` only**, and its body lists what a human finishes: `OMP_VERSION`/`CLINK_VERSION`/`NERD_FONTS_VERSION` in the core, `credits.ts`, `docs/credits.md`, `.github/release-notes.md`, the README, and the parity test. CI then fails on the PR until those are done: that is the gate (spec §6.4: "never lower a test").
- **PRs from the workflow need a token that triggers CI:** `GITHUB_TOKEN`'s PRs do not run `pull_request` workflows; the founder's fine-grained PAT `UPSTREAM_WATCH_TOKEN` (contents: write, pull requests: write, this repo only) does. Without it the workflow still opens the PR and the founder closes and reopens it to run CI (noted in the workflow).

### The fallbacks

- **F1 (U2: quiet `install()` does not relaunch):** Task 3 uses `Update::install` at close instead of its own spawn; `updates\` is not created; `on_before_exit` writes `update.json` and `end_run`.
- **F2 (U3: the own spawn fails to replace the running exe, or shows a window):** "at launch when idle": the download finishes, and when `app_status.busy` is null, no editor has an unsaved change (the UI answers `update_can_install` — a third command) and the lock is free, the app writes `update.json`, `end_run`, and calls `Update::install` (the relaunch of U2 is then wanted); the window disappears and comes back within the installer's time; appendix B records the moment as "ตอนเปิด เมื่อว่าง".
- **F3 (neither F1 nor F2 holds):** "ask to restart": a notify-style card "v<X> is ready: restart CMD Studio to install it" with a button that calls `update_install` (the `app_restart` path with the installer in between); automatic mode behaves as notify for the install step only (the download stays automatic). The founder is told.
